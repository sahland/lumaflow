# LumaFlow Public API Policy

This document defines what constitutes the supported public API of LumaFlow and how that API may evolve.

It complements:

- `docs/architecture/API_DESIGN.md`
- `docs/architecture/adr/ADR-013-component-authoring-model.md`
- `docs/architecture/adr/ADR-020-package-modularity-and-dependencies.md`
- `docs/development/CODING_GUIDELINES.md`

The purpose of this policy is to keep LumaFlow's public surface small, intentional, predictable, and evolvable.

---

# 1. Core Principle

Public API is a compatibility commitment.

A type or member should not become public merely because exposing it makes the current implementation easier.

The default visibility for framework implementation is:

```csharp
internal
```

A symbol becomes public only when it is intentionally part of:

```text
consumer authoring API
official component API
official integration API
documented extension API
```

---

# 2. Public API Categories

LumaFlow recognizes three conceptual API categories:

```text
Stable
Experimental
Internal
```

---

# 3. Stable API

Stable API is intended for normal consumer use and long-term compatibility.

Examples may eventually include:

```text
Widget
StatelessView
State<T>
BuildContext
Text
Button
Row
Column
ThemeData
```

A stable API should:

- have clear semantics;
- have tests;
- be documented;
- have proven consumer usage;
- avoid exposing implementation details.

Before 1.0, stable APIs may still change.

After 1.0, breaking stable API changes require a major version unless explicitly covered by a documented compatibility exception.

---

# 4. Experimental API

Experimental APIs may be exposed when real-world dogfooding requires broader use before the design is fully stable.

They must be clearly labeled.

Possible mechanisms include:

```text
documentation markers
namespace conventions
attributes
release notes
```

Exact mechanism is deferred.

Experimental APIs:

- may change in minor pre-1.0 releases;
- may be removed;
- should not be treated as long-term compatibility contracts;
- must not silently become stable simply because they have existed for some time.

---

# 5. Internal API

Internal API includes implementation details such as:

```text
WidgetNode
BindingScope
mount coordinator
style resolvers
NavigationEntry
OverlayEntry
recycling host internals
diagnostic runtime internals
```

Consumers must not rely on these types.

Internal APIs may change at any time.

---

# 6. Public Surface Budget

LumaFlow intentionally minimizes the number of public symbols.

Before adding a new public symbol, ask:

```text
Can the use case be solved through an existing public abstraction?

Is this required by ordinary consumers?

Is it required by a documented extension point?

Can this remain internal until more usage exists?
```

If the answer supports keeping it internal, keep it internal.

---

# 7. Public Widget API

Ordinary public Widgets should expose semantic configuration.

Preferred:

```csharp
Button(
    "Save",
    variant: ButtonVariant.Primary,
    onPressed: Save
)
```

Avoid exposing implementation details such as:

```text
native Button reference
WidgetNode
mount hooks
style mapper objects
internal binding handles
```

through normal component APIs.

---

# 8. Public Runtime Internals Are Forbidden by Default

Do not expose:

```csharp
public WidgetNode Node { get; }
```

or equivalent solely for advanced customization.

Native UI Toolkit interoperability should provide the escape hatch.

Low-level runtime extension points require deliberate design after framework dogfooding.

---

# 9. Public Native Hierarchy

The exact native `VisualElement` hierarchy generated by a Widget is not a stable public API unless explicitly documented otherwise.

For example:

```text
Button
└── internal VisualElement structure
```

may evolve between compatible releases.

Consumers must not depend on undocumented child order or wrapper count.

---

# 10. Native Element Type Contracts

When LumaFlow explicitly documents that a Widget adapts a particular native control, that mapping may be considered a behavioral contract.

Example:

```text
LumaFlow Button
→ native UI Toolkit Button
```

However, internal wrappers around that control remain implementation details unless documented.

---

# 11. USS Class Names

Generated framework USS classes are internal by default.

Example:

```text
.lumaflow-button
.lumaflow-column
```

must not automatically be considered supported extension points.

A class name becomes public only when explicitly documented as a stable styling hook.

This prevents accidental compatibility obligations around internal selectors.

---

# 12. User-Provided USS Classes

Classes explicitly supplied by consumers remain consumer-controlled data and must be preserved according to the Styling ADR.

LumaFlow must not arbitrarily delete user classes.

---

# 13. Inline Style Behavior

Documented precedence semantics are part of behavioral API:

```text
explicit Widget style
>
component theme
>
global theme
>
framework default
```

Exact internal style mapper implementation is not public API.

---

# 14. BuildContext Surface

Strongly typed foundational context properties may be public:

```text
context.Theme
context.Navigator
context.Overlay
context.MediaQuery
```

once those subsystems are implemented.

Internal provider storage and context derivation implementation remain private/internal.

---

# 15. State<T> Contract

Once public, documented behavior such as:

```text
equality suppression
subscription notification semantics
ownership semantics
threading semantics
```

is behavioral API.

Changing those semantics can be breaking even if method signatures remain identical.

---

# 16. Behavioral Compatibility

Public API compatibility includes more than compilation.

A change may be breaking if existing valid code still compiles but meaningfully changes behavior.

Examples:

```text
State<T> now sends duplicate notifications
Button callbacks fire twice
theme precedence changes
Pop() changes root behavior
Native(existingElement) begins silently reparenting
```

Behavioral contracts documented by ADRs/user documentation must be considered during compatibility review.

---

# 17. Lifecycle Compatibility

Documented ownership and lifecycle behavior is public behavior.

Examples:

```text
MountHandle.Dispose() unmounts its subtree
external State<T> is not disposed by WidgetNode
borrowed VisualElement is not destroyed
popped route is cleaned deterministically
```

These must not change casually.

---

# 18. Exception Compatibility

Exception message wording is not stable API unless explicitly documented.

Consumers should not parse full exception strings.

Exception types may become API when callers are reasonably expected to distinguish them.

Tests should avoid asserting entire exact message strings.

---

# 19. Diagnostic IDs

If LumaFlow later introduces stable diagnostic codes such as:

```text
LF1001
LF2004
```

those codes may become compatibility contracts.

Do not introduce them until long-term maintenance value justifies it.

---

# 20. Constructors

Changing a public constructor can be breaking.

Particularly:

```text
removing parameter
changing parameter type
changing required/optional status
changing semantic meaning
reordering positional parameters
```

should be treated carefully.

---

# 21. Optional Parameters

Adding an optional parameter is generally source-compatible but can still affect overload resolution.

API review must consider C# overload ambiguity.

---

# 22. Overloads

Do not create large families of subtly different overloads.

Prefer a clear primary API using:

```text
required core arguments
+
named optional arguments
```

where possible.

Overload additions must be reviewed for ambiguity.

---

# 23. Parameter Names

Because C# consumers may use named arguments, public parameter names are part of practical source compatibility.

After 1.0, renaming:

```csharp
onPressed:
```

to:

```csharp
callback:
```

can break consumer code even if type signatures are otherwise identical.

Treat public parameter names deliberately.

---

# 24. Enum Compatibility

Adding enum values can affect consumers that use exhaustive switches.

Therefore enum additions should be treated as potentially compatibility-sensitive.

Prefer enums for genuinely closed semantic sets, but document when future values may be introduced.

---

# 25. Enum Renaming and Removal

Removing or renaming public enum values is breaking.

Use deprecation where appropriate after 1.0.

---

# 26. Public Interfaces

Adding members to a public interface is usually breaking for external implementers.

Therefore avoid publishing large framework interfaces before extension requirements are proven.

Prefer sealed or concrete consumer types when substitution is not required.

---

# 27. Public Abstract Classes

Adding abstract members to a public abstract class is breaking for derived implementations.

Low-level custom Widget extension base classes should therefore be designed conservatively.

Do not expose them before real third-party-like usage has been tested.

---

# 28. Virtual Members

Every virtual/protected extension point creates long-term behavioral obligations.

Do not mark methods virtual merely to make a class "extensible."

Composition is preferred.

---

# 29. Public Generic Constraints

Changing generic constraints can be breaking.

Keep them minimal and semantically justified.

---

# 30. Namespaces

Public namespace changes are breaking.

Use pre-1.0 development and dogfooding to settle namespace structure before 1.0.

Avoid reorganizing namespaces based solely on folder structure.

---

# 31. Assembly Names

Assembly names may be referenced by consumers and integrations.

Treat stable public assembly names deliberately, especially after 1.0.

---

# 32. Pre-1.0 Policy

Before `1.0.0`, LumaFlow prioritizes reaching a clean architecture over indefinite backward compatibility.

Breaking changes are allowed when they materially improve the framework.

However every breaking change should be:

```text
intentional
documented
tested
reflected in samples
reflected in user documentation
```

Do not accumulate compatibility shims for every early prototype API.

---

# 33. Pre-1.0 Experimental Default

Before 1.0, newly introduced high-level APIs may still evolve.

However accepted architectural invariants should not be violated casually.

Pre-1.0 does not mean architectural behavior is random.

---

# 34. 1.0 Stability Gate

A public API should not be considered 1.0-stable until:

```text
it has tests
it has documentation
it has real dogfood usage
its ownership is clear
its lifecycle is clear
its threading behavior is clear
its native interoperability behavior is clear
```

where applicable.

---

# 35. Post-1.0 Breaking Changes

After 1.0, breaking stable API changes require a major version unless correcting a severe defect or security problem requires otherwise.

Such exceptions must be documented clearly.

---

# 36. Deprecation

After 1.0, prefer deprecation before removal where practical.

Conceptually:

```text
Version N:
old API marked obsolete
new API introduced

Version N+1 or next major:
old API removed according to policy
```

Exact deprecation duration may depend on project maturity.

---

# 37. Obsolete Attributes

Use `[Obsolete]` with actionable migration guidance.

Good:

```text
Use Button(onPressed: ...) instead.
```

Bad:

```text
Deprecated.
```

---

# 38. Do Not Preserve Bad APIs Forever

Compatibility has cost.

A major release may intentionally remove obsolete or harmful APIs.

The goal is predictable evolution, not permanent support for every historical mistake.

---

# 39. Native Interop Compatibility

LumaFlow must preserve documented native escape hatches.

A compatible release should not unnecessarily make it harder to:

```text
embed VisualElement
use USS
use UXML
mount into existing native roots
use UI Toolkit debugging
```

unless a clear architectural reason exists.

---

# 40. Experimental Native Hooks

Access to internal native structures is not stable merely because reflection or hierarchy traversal makes it possible.

Only documented hooks are supported.

---

# 41. Third-Party Extension API

Third-party extension points must be intentionally designed.

Before stabilizing them:

```text
implement several built-in components
implement Native interop
implement StatefulView
dogfood AudioLib
create at least one third-party-like test component
```

Then expose the smallest necessary low-level API.

---

# 42. No Reflection Contract

Consumers must not be expected to discover or modify private framework implementation through reflection.

Such usage is unsupported.

---

# 43. Public API Review Checklist

Before making a symbol public:

```text
[ ] Is ordinary consumer code expected to use it?
[ ] Is its responsibility clear?
[ ] Is ownership documented?
[ ] Is lifecycle documented?
[ ] Is threading behavior documented if relevant?
[ ] Can its implementation change without breaking consumers?
[ ] Is a smaller API possible?
[ ] Has realistic consumer syntax been reviewed?
```

---

# 44. Breaking Change Review Checklist

Before accepting a potentially breaking change:

```text
[ ] Does source code stop compiling?
[ ] Do named arguments break?
[ ] Does runtime behavior change?
[ ] Does lifecycle/ownership change?
[ ] Does native hierarchy contract change?
[ ] Does documented USS behavior change?
[ ] Does exception classification change?
[ ] Do samples/docs need migration?
```

---

# 45. Codex Rules

Codex must:

1. prefer `internal` for implementation details;
2. not expose WidgetNode/runtime internals for convenience;
3. inspect existing public API before adding overloads;
4. treat parameter names as compatibility-sensitive;
5. not treat generated USS classes as stable API unless documented;
6. not rely on exact native child hierarchy as consumer contract unless documented;
7. update tests/docs when changing public behavior;
8. preserve behavioral contracts even when signatures remain unchanged;
9. avoid premature extension interfaces/base classes;
10. flag significant public API expansion for deliberate review.

---

# 46. Final Principle

LumaFlow's public API should be smaller than its implementation.

The framework should expose concepts consumers need, not every mechanism used internally.

The guiding rule is:

**Every public symbol is a promise.  
Make as few promises as necessary, and make each one precise.**
