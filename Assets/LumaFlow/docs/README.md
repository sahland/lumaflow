# Инструкция по коммитам и MR

Этот документ описывает обязательный порядок работы с ветками, коммитами и MR.

## Обязательный flow

1. Обновляем локальный `main`.
2. Создаем новую ветку только от `main`.
3. Делаем задачу в своей ветке.
4. Мержим свою ветку в `dev`.
5. Тестируем изменения локально и проверяем, что задача не ломает общий сценарий.
6. После проверки мержим эту же рабочую ветку в `main`.

Важно: `dev` никогда не мержим в `main`.

В `main` попадает только рабочая ветка с задачей. Если в `dev` уже есть чужие или непроверенные изменения, они не должны уехать в `main` вместе с вашей задачей.

## Пример

```bash
git checkout main
git pull
git checkout -b feature/task-name

# работа над задачей
git add .
git commit -m "feat: task-name"
git push -u origin feature/task-name
```

Дальше создаем MR:

1. `feature/task-name` -> `dev`
2. проверяем локально
3. `feature/task-name` -> `main`

## Описание MR

При каждом MR в `dev` или `main` в отдельном треде/комментарии обязательно пишем:

- что это за задача;
- что было реализовано;
- что нужно проверить;
- есть ли миграции, новые переменные окружения, настройки или ручные действия;
- есть ли риски или известные ограничения.

Минимальный пример:

```text
Задача: добавлена авторизация по SMS.
Реализовано: endpoint отправки кода, проверка кода, обработка повторной отправки.
Проверить: успешный вход, неверный код, повторная отправка через таймер.
Дополнительно: нужна переменная SMS_API_TOKEN.
```

## Коммиты

Коммиты должны помогать понять историю изменений, но без театра.

Хорошо:

```text
feat: add sms login
fix: handle empty user phone
refactor: simplify payment status check
docs: update MER flow
```

Если очень хочется написать `блядь, сука`, можно. Один раз выдохнули, посмеялись, пошли дальше. Но для общей истории лучше оставлять хотя бы минимальный смысл: что изменилось и зачем.

## Базовые правила

- Одна ветка - одна задача.
- Не смешиваем несколько независимых задач в одном MR.
- Перед MR подтягиваем свежий `main` и решаем конфликты в своей ветке.
- Не коммитим секреты, `.env`, токены, ключи и локальные настройки.
- Не отправляем в MR временный мусор: логи, дампы, архивы, сгенерированные файлы без необходимости.
- Если изменение затрагивает несколько сервисов или фронтенд, пишем это в описании MR.
- Если тесты не запускались, честно пишем об этом в комментарии.

## Перед мержем

Проверьте короткий список:

- задача сделана в отдельной ветке от `main`;
- ветка уже проверена через `dev`;
- локальная проверка выполнена;
- описание MR заполнено;
- в `main` мержится рабочая ветка, а не `dev`.
